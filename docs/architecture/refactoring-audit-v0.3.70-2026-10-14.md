## 3. Остаточные зависимости, значимые для надёжности

### R-01. Удаление активного аккаунта во время загрузки папки

**Приоритет проверки: высокий по потенциальному ущербу, но пользовательского воспроизведения нет.**

`MainWindow.AccountContextMenu.cs:RemoveSavedAccountAsync` после подтверждения удаляет сохранённую авторизацию, затем выполняет асинхронное удаление профиля; для активного аккаунта очищает рабочие поля, строки и источник папок. В этом методе не повышается `_accountSwitchGeneration` и не ожидается незавершённая `LoadFolderAsync`.

В `MainWindow.xaml.cs:LoadFolderAsync` проверка `IsStaleAccountSwitch()` применяется, только если при вызове было передано необязательное `accountSwitchGeneration`; обычная загрузка передаёт `null`. Поэтому существует обоснованный по управляющим ветвям риск, что завершившийся ответ ранее открытого аккаунта повторно заполнит `_currentMessages` / `_currentFolderId` и представление после удаления, либо перезапишет статус. Это **гипотеза о достижимости последовательности по коду**, а не зарегистрированный сбой и не доказательство внешней отправки данных.

**Учёт:** задача GitHub [#166](https://github.com/lvlaksim1/mailru-desktop/issues/166).

**Первое необходимое действие:** автономное воспроизведение с контролируемо задержанным ответом без доступа к реальным почтовым ящикам. Условия: (1) загрузка A начата; (2) владелец подтверждает удаление A; (3) ответ загрузки приходит поздно; (4) удалённая папка не публикуется, A не возвращается, другой аккаунт не затронут; (5) сохранённая авторизация не восстанавливается. Только если проверка выявит дефект — точечная защита поколения/владельца результата. Не менять HTTP и не экспериментировать на реальных аккаунтах.

### R-02. Переключение через скрытый `LoginComboBox`

`MainWindow.xaml` содержит `LoginComboBox` с `Visibility="Collapsed"`; основной активный интерфейс использует `AccountRailListBox`, у которого есть поколение и сериализация. Скрытый обработчик `LoginComboBox_SelectionChanged` вызывает `RestoreSavedAuthorization` напрямую; при неконтролируемом срабатывании на фоне загрузки его поведение отличается.

**Решение:** не трактовать это как пользовательский дефект без подтверждения пути вызова. Проверить программные изменения выбранного элемента и защиту `_updatingAccountSelection`; не вводить вторую схему переключения и не удалять код по догадке.

### R-03. Переход по уведомлению и текущий выбор папки

`MainWindow.PushNotifications.cs:NavigateToPushMailAsync` использует `_accountSwitchGate`, поколение и поиск **по точному идентификатору письма**. Во время последующего серверного поиска могут происходить новые действия пользователя; текущие испытания не эквивалентны всем комбинациям. Повода объявлять уведомления неисправными нет.

**Решение:** при необходимости добавить автономные испытания одновременного перехода из уведомления, смены папки и аккаунта; не перерабатывать MCS/PushMe и механизм уведомлений без фактов.

### R-04. Отдельные незавершённые функциональные задачи

Задача #77 (безопасная отправка ранее отложенного письма), реальная выдача более 200 результатов поиска и неизвестная первопричина прежнего временного отказа авторизации — **не дефекты структуры `MainWindow` и не основание для массового рефакторинга**. Сохранять отдельный учёт и собственные условия приёмки.

## 4. Решение о дальнейшем объёме

**Сейчас обязательного массового рефакторинга нет.** Подтверждённое пользователем поведение v0.3.70 имеет приоритет перед уменьшением строк или числа `partial`-файлов.

Порядок работы:
1. **R-01:** сначала воспроизводимая проверка пограничного случая удаления во время загрузки. Возможное изменение — узкая защита от устаревшего результата, отдельная ветка, автономная проверка, Windows CI, пользовательская приёмка.
2. **R-02:** проверить достижимость скрытого пути переключения аккаунта, не менять код без основания.
3. **R-03:** оставить на контролируемое испытание, если появится воспроизводимый случай или новая функция уведомлений.
4. **Прочее:** не выделять дополнительные WPF-компоненты только ради структуры. `MailReaderHeader` оставлен стабильным; второй браузер в основном представлении запрещён; WebView2 и эталонный разделитель не изменять.
5. **После любых подтверждённых изменений:** повторить автономные испытания, WPF, проверку переходов и реальную приёмку. Не объединять непроверенную ветку и не создавать официальный релиз по одному успешному компилированию.

**Итог:** переход от большого плана переработки v0.3.54 к адресным проверкам согласованности данных. Следующая разумная единица работы — **проверка R-01, а не выделение нового визуального класса**. Этот документ не является разрешением на удаление пользовательских аккаунтов или реальную отправку почты при испытаниях.
