# Реестр окон и элементов MailRu Desktop

В репозитории хранится **проверяемый каталог всех окон и элементов интерфейса**:
[ui-registry.json](ui-registry.json). Он автоматически строится на основании
исходной разметки XAML и создания элементов WPF в коде C#.

## Состав каждой записи

Для **окон**: уникальный идентификатор, путь к исходному файлу, способ
создания (XAML/программный), начальная геометрия, цветовые свойства, правила
шрифта, количество элементов.

Для **элементов**: устойчивый по исходной разметке идентификатор, родитель,
окно-владелец, тип, имя `x:Name` (если задано), файл, свойства расположения
(размеры, ограничения, отступы, ряд/столбец сетки), цветовые свойства/роли,
шрифты, применённый стиль и определения состояний (наведение, фокус, нажатие,
выделение), когда они присутствуют в источнике.

У программно создаваемых элементов вместо полного положения в дереве
фиксируются место их создания в исходном файле и непосредственно
объявленные свойства. Это **не означает**, что координаты таких элементов
всегда известны статически: окончательная геометрия определяется WPF при
построении окна. Не выдумывать значения, отсутствующие в исходном коде.

## Окна, создаваемые в ходе работы

Программно создаваемый объект `new Window` регистрируется как отдельное окно,
даже если он объявлен в файле частичного класса основного окна. Программно
создаваемые после него дочерние элементы учитываются в соответствующем окне.

Для редактора нового письма исходная разметка `ComposeWorkspace` сохраняется
в файле основного окна и переносится в отдельное окно при открытии. В каталоге
для такого поддерева указан `runtime_host_window`: исходное расположение в
разметке и фактическое окно размещения различаются. Это предотвращает
пропуск окон, создаваемых без отдельного XAML.

## Изменение интерфейса

1. Добавить или изменить окно/элемент в исходном коде.
2. Использовать цвета из [26 фиксированных ролей](theme-palette.md),
   включая состояния `IsMouseOver`, `IsPressed`, `IsKeyboardFocused`,
   `IsSelected` и `IsEnabled=False`. Не оставлять стандартное оформление
   Windows с неподконтрольными цветами (как было в кнопке «Почта»).
3. Использовать ресурсы `AppFont*Size`. Основной размер задаётся пользователем
   в диапазоне 10–18; группа/назначение элемента определяет производный размер,
   но пользователь не меняет взаимосвязь элементов с ролями.
4. Сохранить автоматический каталог командой
   `python tools/ui_registry.py --write`.
5. Проверить командой `python tools/ui_registry.py --check`.
   В обязательной сборке проверка завершится ошибкой, если каталог не
   соответствует исходникам. Таким образом, новый элемент нельзя пропустить
   из реестра незаметно.

Каталог **не является второй вручную поддерживаемой копией интерфейса**.
Он воспроизводим из исходных файлов и служит снимком для проверки изменений.

## Исключения

Изображения, реальные фотографии отправителей, HTML-содержимое полученных
писем и фирменные обозначения сторонних организаций не перекрашиваются.

Геометрия, создаваемая динамически с учётом размера окна, положения
разделителей и размера текста, фиксируется в каталоге как правило или
выражение, а не как вымышленная статическая координата.

## Контроль полноты

Проверка перечисляет все XAML-узлы (включая неназванные и определения
шаблонов), программно создаваемые элементы из исходников, декларации окон,
свойства цветов/шрифтов и состояния. Она также указывает окно-родителя.
Сведения можно искать по имени, исходному файлу и типу.

Код проверки и генерации: [tools/ui_registry.py](../tools/ui_registry.py).

## Дополнительные проверки

В каталог включены не только определения окон, но и общие ресурсы
`App.xaml`, все словари оформления (включая `ThemeStyles.xaml`),
программно сформированные шаблоны и создаваемые в C# элементы.

Система проверяет, что каждая ссылка в разметке на ресурс цвета вида
`App…Brush` соответствует существующей роли каталога `ThemePalette`.
Несуществующая роль вызывает ошибку проверки. В настоящее время
объявлено 26 цветовых ролей; число ссылок и используемых ролей
фиксируется в разделе `color_reference_audit` сформированного файла.

Изначальные 26 ролей не переопределяются пользователем: настраиваются
их значения, но не состав элементов. Это правило применяется
ко всем вновь разрабатываемым окнам.
