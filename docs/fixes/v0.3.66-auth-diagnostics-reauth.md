# MailRu Desktop v0.3.66 — диагностика авторизации и повторный вход в выбранный аккаунт

Дата: 14.10.2026. Основание: массовые отказы при проверке 27 из 32 аккаунтов после установки v0.3.65, наблюдение владельца и diagnostics.log. Истинная причина не доказана. Ранее в коде сбой обновления токена создавал местную ошибку 403, неотличимую от ответа Mail.ru.

## Диагностические изменения

- В журнале `%LOCALAPPDATA%\\MailRuDesktop\\diagnostics.log` категория `auth_token_flow` отделяет `initial_access`, `refresh_token`, `refresh_request`, `refresh_response`, `verify_new_access`, `store` и общий результат.
- Разделяются ветки `active_folder` и `background_counter`. Регистрируются HTTP-коды реального ответа при отказах 401/403 и при обновлении (например, 400/429/500), а также источник кода (`http_response`, `json_status`, `local_refresh_result`). Код 403, сформированный приложением, не называется серверным.
- Аккаунты обозначаются `ACCOUNT_001`, `ACCOUNT_002` и так далее в порядке их сохранённого списка, без записи электронного адреса. Самих токенов, паролей, cookie, серверных тел и адресов почты новые записи не содержат.
- При одновременных отказах фоновой проверки соблюдается пауза 5 секунд после отказа, чтобы не посылать серию одинаково неуспешных запросов.
- Запоздалый результат автоматического обновления не перезаписывает новые токены, полученные повторным входом; используется сравнение исходного сохранённого токена.
- При ошибке обновления существующие данные не стираются; сообщение в интерфейсе перестало без доказательств утверждать, что Mail.ru отверг сохранённый токен.

## Повторная авторизация

В контекстном меню **конкретного аккаунта**: «Повторная авторизация», рядом с прежним «Удалить». Открывается привычная форма ввода пароля, но адрес выбранного аккаунта заранее заполнен и недоступен для редактирования. Сначала выполняется штатная авторизация через существующий aj-https.mail.ru, затем проверка нового токена чтением папки без модификации почты. **Только после успеха** обновляются токены этого аккаунта. Остальные аккаунты, порядок разделов и действующая активная почта не изменяются. При отказе пароль и старые токены остаются без изменений. Для активного аккаунта выполняется обновление его текущей папки.

## Испытания и ограничения

Нужны CI Windows (сборка, InteractionLogicSmoke, WindowsUiSmoke, реестр элементов и проверка запуска) и проверка на компьютере владельца. Автономные испытания охватывают HTTP-код обновления, отсутствие идентифицирующих данных, защиту от запоздалой записи, меню конкретного аккаунта, фиксированный адрес повторного входа и сохранение обычного добавления аккаунта.

**Проверка владельца:** после обновления открыть `diagnostics.log`, проверить этапы на одном проблемном аккаунте; затем выбрать в контекстном меню одного аккаунта «Повторная авторизация», убедиться, что чужие аккаунты не изменены. Не выполнять одновременное массовое повторное добавление аккаунтов. Окончательная причина первоначальной массовой ошибки пока не установлена.

Никакой новый протокол и новые HTTP-маршруты не добавлены, настройки и сохранённая авторизация при установке не удаляются. Этап 3 общего рефакторинга почтовых команд остаётся отложенным.
