# Android Mail.ru 15.107.0.148045: новые письма и уведомления

Дата: 2026-10-09. Статус доказательств: анализ сохранённого исходного кода APK; **живой обмен сервера и путь до системного уведомления Android ещё не наблюдались**. Версия источника: ветка `research/mail-apk-15.107.0.148045`, коммит `b4944d3c49e5c83e0cf896ad35eb6748b2177015`.

## Установлено непосредственно по APK

1. `decompiled/relevant/ru/mail/util/push/pusher/params/PushMeParamsPreparerImpl.java` содержит действующий построитель набора подписок на уведомления. Для каждого `PushInfoProvider` читается собственный `pushToken`, а через `AuthProvider.getServiceToken` — средство подтверждения права доступа конкретного аккаунта. Если токен службы отсутствует, поставщик пропускается; если отсутствует токен аккаунта, формирование заканчивается ошибкой. Дубликаты аккаунтов при обработке одного поставщика исключаются.
2. При формировании записи `fillRootJSON` включает `status=0`, `account`, `platform`, `application`, `token` (токен доставщика), `settings`, `access_token` (почтовый токен, если применим), `mpop` (если вместо него используется cookie), `android_id`, `sdk_device_id`. В параметрах `settings` присутствуют `badge` с `mode=unread` и `status`, `capabilities`, сведения о клиенте и `device_id`. Это регистрационная модель, а не обычное получение списка писем.
3. `getPlatform(PushType)`: `HMS` → `huawei`, `VKPNS` → `vkpns`, все остальные значения → `android`. Точный программный поставщик ветки `android` по одному этому файлу не установлен. Токен доставки уведомлений **не равен** почтовому OAuth `access_token`.
4. В `decompiled/relevant/com/vk/pushme/network/model/request/InternalSubscriptionRequest.java` обнаружена модель другого связанного компонента подписки: `account`, `application`, `platform`/transport, `token`/pushToken, `access_token`, `android_id`, `sdk_device_id`, `settings`, `status`. Это независимое подтверждение структуры; один файл не доказывает, что именно этот клиент вызывает этот запрос при каждом входе.
5. В `APK_HOST_RESOURCES.md` (`resources.arsc`) статический `push_default_host` равен `alt-push-me.mail.ru`, тестовый `push_default_host_dev` — `push-me.devmail.ru`, схема `https`. Присутствуют строковые признаки `push-me.mail.ru`. **Конкретный путь подписки/снятия подписки, формат входящего события и действующий сервер без трассировки не подтверждены.**

## Что НЕ установлено

- Какая служба (Firebase/Google, Huawei или VK) фактически доставляет события на устройстве в конкретной среде; дефолтное значение `android` само по себе не доказывает использование Firebase.
- Какой класс приёма события обрабатывает новое письмо, какое содержимое передаётся в уведомлении, как он обновляет список/счётчик и показывает системное уведомление, есть ли повторная доставка и объединение событий.
- Реальная скорость, гарантии доставки, поведение при отключении сети, выгрузке приложения и возобновлении работы; резервный периодический опрос в Android не установлен.
- Пригодность Android-токена поставщика для Windows (считать **не доказанной**). Нельзя выдавать наличие регистрации для Android за готовый независимый Windows-канал.
- В исследовательской ветке сохранено 446 отобранных исходных файлов, преимущественно сетевого слоя; полная служба приёма уведомлений не входит в исследованный набор. Полный исходный APK сохранён частями в `package/parts` и пригоден для дополнительного целевого анализа.

## Сравнение с MailRu Desktop v0.3.32

`src/MailRuDesktop.App/MainWindow.FolderCounters.cs`: `DispatcherTimer` каждые **90 секунд**, активная учётная запись/папка, запрос `GetFolderThreadsAsync(token, folder, 0, 1)`, чтение явных счётчиков, локальная корректировка данных интерфейса. Это **не сигнал о новом письме**, не обновление списка по появившемуся ID и не системное уведомление. `RefreshAccountUnreadCountsAsync` проходит по сохранённым аккаунтам при первоначальной загрузке; непрерывного одинакового цикла по всем аккаунтам здесь не выявлено.

## Применение в Windows (предложение, не решение к реализации)

1. Не копировать слепо Android-регистрацию: для Windows требуется независимо доказать доступный транспорт доставщика событий и право клиента на него. До этого предпочтителен проверяемый собственный механизм обновления.
2. Для первой реализации — фоновая проверка новых **идентификаторов** писем по каждому авторизованному аккаунту с ограничением параллелизма, разумным изменяемым периодом и немедленной сверкой после пробуждения/восстановления сети. Интервал и нагрузку определять опытами, а не объявлять реальные уведомления «мгновенными».
3. При первом подключении считать текущие письма исходным состоянием, не показывать их как новые. При следующей сверке сравнивать пару `(account, message_id)`, обновлять реестр писем без потери выделения/прокрутки, отправлять системное уведомление Windows не больше одного раза на новое письмо, уважать настройку пользователя.
4. Счётчик непрочитанных сохранять как отдельное состояние: его увеличение/уменьшение не является надёжным доказательством поступления нового письма. При ошибках не обнулять известные данные. Добавить отмену запоздалых запросов, ограничение запросов на сеть, восстановление токена и постепенное увеличение паузы после ошибок.
5. Отдельное целевое исследование полного APK: найти регистрацию служебных компонентов Android, слушатель уведомления, точки обновления почты и условия повторной подписки; затем, при разрешении владельца, выполнить безвредное испытание с тестовым ящиком для точного подтверждения сервера/формата и сравнительных задержек.

Документ фиксирует только проверенные статические факты и отдельно обозначает технические гипотезы. Никакие пользовательские токены или частные письма не записаны.
