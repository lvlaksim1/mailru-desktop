## Состав исследовательской программы

Исходный код хранится **только в исследовательской ветке**, без накопления скомпилированных программ в истории Git:

- `tools/push_research/google_sender_probe.py` — непосредственный эксперимент с Google Check-in, register3, MCS и исходными идентификаторами Android APK.
- `tools/push_research/pushme_contract_probe.py` — составление одного запроса подписки, строгая классификация ответа `validate_result`; настоящих почтовых запросов нет.
- `tools/push_research/local_mailru_event_probe.py` — отдельная локальная последовательность Google → MCS → PushMe → событие; читает защищённый `AccessToken` из текущей пользовательской `%LOCALAPPDATA%\MailRuDesktop\auth.json` с помощью Windows DPAPI только после явного разрешения запуска.
- `tools/push_research/test_local_probe.py` — проверки с искусственными ответами; никакого реального почтового содержимого.
- `tools/push_research/Start_Push_Trial.cmd` — консольный запуск с явным подтверждением `YES`.

Фактическая последовательность локального сценария: чтение существующего токена выбранного аккаунта на компьютере пользователя → создание отдельного адреса Google для нового получателя → защищённый вход в `mtalk.google.com:5228` → одна подписка `POST https://alt-push-me.mail.ru/api/v2/set_settings` для **выбранного** аккаунта → ожидание `event=4` → `POST /api/v2/unsubscribe_by_token` только для временного адреса компьютера. Существующий телефонный токен и устройство не читаются и не удаляются. Программа не отправляет письма.

## Меры предосторожности

- Без `--live --subscribe --login` сетевых обращений и чтения почтовых данных **нет**.
- Почтовые токены и учётные данные Google не передаются в GitHub, не записываются в журналы и не печатаются в консоль.
- Аутентификация использует **только** уже подключённый аккаунт и системный механизм защиты данных Windows.
- В журнале отображаются обезличенные `ACCOUNT_ACCEPTED`, `MAILRU_NEW_MAIL_EVENT_RECEIVED=YES`, состояние удаления собственного токена.
- Исходный APK и сертификат проверены; **не создаём** новый проект Mail.ru или собственную регистрацию почтового приложения.
- Для снижения ненужной серверной нагрузки между исследовательскими обращениями предусмотрена пауза ≥5 секунд.

## Открытые ограничения перед реальным испытанием

1. **Точные настройки `capabilities` и карты клиента из оригинального APK:** необходимо завершить сохранение исходников `CapabilitiesProviderFactory` и связанных классов, а не применять приблизительные поля. В заготовке локального клиента пока `capabilities={}`; это может исключить доставку событий.
2. **Принятие токена Mail.ru сервером:** даже `Login_OK` Google не доказывает, что сервер PushMe считает новый независимый токен допустимым.
3. **Фактический конец цепочки:** нужно реально увидеть `event=4` и сопоставить с отправленным на собственный испытательный ящик письмом.
4. **Доставка в долгоживущем соединении:** повторное подключение, сердцебиение, подтверждение полученных сообщений и исключение дублей пока не исследованы в продуктивном режиме.
5. **Параметры клиента:** сам факт успешного `POST` без `validate_result.account.is_valid=true` не должен трактоваться как подтверждение подписки.
6. **Очистка:** скрипт выполняет `unsubscribe_by_token` для своего токена в `finally`, но если связь потеряна и ответ сервера не получен, окончательное удаление может остаться неподтверждённым.

## Граница допуска

Проверки с настоящим OAuth-токеном не должны выполняться в общедоступной системе GitHub Actions. Локальный запуск под учётной записью владельца проводится только когда подтверждены параметры подписки и доступна разрешённая испытательная среда.

**Подключение механизма к рабочей версии MailRu Desktop пока не разрешено техническими результатами.**

## Дополнительная проверка выбора версии API

В сохранённом исходнике оригинального APK `com/vk/pushme/logic/usecase/SubscriptionUseCase.java` метод `isV1(application)` **безусловно возвращает `false`**. Для активной системы PushMeSdk это исключает использование ветки V1 при выборе версии подписки; подходящий путь — `/api/v2/set_settings`. Данный вывод относится именно к SDK текущего APK и не отменяет наличия старых команд V1 в архиве.

При построении `SubscriptionRequest` SDK приводит название аккаунта к нижнему регистру, получает OAuth-токен для каждого аккаунта отдельно и устанавливает `status=0`. Наш изолированный обработчик использует те же признаки; успешная регистрация настоящего аккаунта по-прежнему требует живой проверки.
