# Отложенная отправка: условия безопасной немедленной отправки

Состояние: **заблокировано для боевого интерфейса**. Основание: задача [№ 77](https://github.com/lvlaksim1/mailru-desktop/issues/77).

## Что подтверждено исходным кодом

- `POST /api/v1/messages/schedule` создаёт планируемую отправку по `send_date`.
- `POST /api/v1/messages/send` создаёт обычную отправку. Существующий `MailRuClient.SendMessageAsync` выбирает один из этих двух путей по переданному времени.
- Наличие `source.schedule` в данных нового сообщения само по себе не доказывает, что сервер отменяет ранее зарегистрированное расписание и повторно использует исходную запись.
- В подтверждённом перечне команд MailRu Desktop **нет проверенной атомарной операции**, которая переводит уже запланированное сообщение в отправленное и отменяет исходную задачу сервера.

## Почему нельзя включить кнопку

Отправка нового сообщения с тем же адресатом, темой и текстом без подтверждённой отмены прежней задачи может привести к двум отправкам. Удаление письма из папки «Исходящие» тоже нельзя считать доказательством отмены расписания.

## Требуемое исследование перед разблокировкой

1. Получить из разрешённого тестового почтового ящика идентификатор и полное состояние **уже созданного** запланированного письма, отличая ID сообщения от ID задания по расписанию.
2. По официальному клиенту Mail.ru определить существующую операцию «Отправить сейчас» над этим объектом, точные параметры запроса и ответы, без предположений о маршруте.
3. На тестовом письме с будущим временем и единственным собственным адресатом проверить, что операция изменяет именно исходное задание, и что после неё исходное расписание отсутствует.
4. Сверить отправленные сообщения и фактическую доставку в течение исходного интервала расписания — один исходный ID и не более одной отправки.
5. Проверить отказ, тайм-аут, повторное нажатие, два одновременных запроса и восстановление после перезапуска; не допустить повторной отправки после неопределённого ответа.
6. Только после этого включить одиночное и массовое действие и добавить воспроизводимые автономные испытания.

Исследовательские внешние запросы выполняются с интервалом **не менее 5 секунд**. Секреты, токены и полные тексты писем в репозиторий не загружать.

**Решение:** не включать потенциально опасную команду без протокольного и сквозного подтверждения. Это открытый технический долг, не функция v0.3.30.

## Проверка 14.10.2026 — подготовлен автономный анализ записей

Проверено в исходниках текущей официальной v0.3.71: клиент умеет создавать
новое письмо через `/api/v1/messages/send` и новое расписание через
`/api/v1/messages/schedule`. В ответах/записях проекта **не найдено**
подтверждения отдельной команды, которая использует уже существующий ID
отложенного сообщения и отменяет прежнее задание без дубликатов.
Поиск открытых сторонних исходников также не дал пригодного подтверждения.
Кнопки `BulkSendNowButton` и `PreviewSendNowButton` пока намеренно выключены.

**Добавлено вспомогательное исследование, не функция приложения:**
`tools/inspect_scheduled_send_zip.py` читает архив `.research.zip`
проекта APK Research, журнал `02_normalized/http-transactions.jsonl` и
ограниченные тела запросов. Запускается автономно, **ничего не отправляет**
и выводит только безопасные сведения о запросах к `aj-https.mail.ru`:
метод, маршрут без идентификаторов и параметров URL, разрешённые имена
полей, признак заполненного `source.schedule` и статус ответа.
Токены, адресаты, темы, текст, ID сообщений и само содержимое архива
в результат не записываются. Скрипт всегда возвращает
`safe_send_now_operation_verified=false`, поскольку
даже увиденный запрос не доказывает однократность доставки.

Пример локального анализа:
```
python tools/inspect_scheduled_send_zip.py "<запись>.research.zip" > send-now-redacted.json
```
Скрипт не нужен внутри работающего MailRu Desktop и не изменяет его
сетевые настройки или релизы.

### Недостающий опыт в разрешённом тестовом аккаунте

1. Открыть официальный клиент Mail.ru в APK Research на тестовом
   аккаунте; проверить, что запись HTTPS-запросов действительно работает.
2. Создать **единственное** отложенное письмо на собственный тестовый
   адрес с безопасной темой и временем достаточно далеко в будущем.
   Сохранить наблюдаемую операцию создания и её ответ.
3. Начать отдельную запись, выбрать уже отложенное письмо и штатное
   действие «Отправить сейчас» в официальном клиенте (если оно доступно).
   Не корректировать и не воспроизводить HTTP-запросы вручную.
4. Зафиксировать ответ сервера и состояние папок после действия; повторно
   проверить отсутствие отложенной задачи к первоначальному времени.
5. Предоставить архив записи для обезличенного разбора: сами файлы могут
   содержать секреты, поэтому не публиковать их в открытом GitHub.
   В репозиторий допускается только обезличенный структурный отчёт.
6. Проверить отсутствие второй отправки после наступления исходного срока,
   а также реакцию на тайм-аут и повторное нажатие на тестовом письме.

**До доказательства отмены исходного расписания и защиты от дубликатов
функция «Отправить сейчас» остаётся заблокированной.**
