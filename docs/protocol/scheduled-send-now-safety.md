# Отложенная отправка: условия безопасной немедленной отправки

Состояние: **заблокировано для боевого интерфейса**. Основание: задача [№ 77](https://github.com/lvlaksim1/mailru-desktop/issues/77).

## Что подтверждено исходным кодом

- `POST /api/v1/messages/schedule` создаёт планируемую отправку по `send_date`.
- `POST /api/v1/messages/send` создаёт обычную отправку. Существующий `MailRuClient.SendMessageAsync` выбирает один из этих двух путей по переданному времени.
- Наличие `source.schedule` в данных нового сообщения само по себе не доказывает, что сервер отменяет ранее зарегистрированное расписание и повторно использует исходную запись.
- В подтверждённом перечне команд MailRu Desktop **нет проверенной атомарной операции**, которая переводит уже запланированное сообщение в отправленное и отменяет исходную задачу сервера.

## Почему нельзя включить кнопку

Отправка нового сообщения с тем же адресатом, темой и текстом без подтверждённой отмены прежней задачи может привести к двум отправкам. Удаление письма из папки «Исходящие» тоже нельзя считать доказательством отмены расписания.

## Требуемое исследование перед разблокировкой

1. Получить из разрешённого тестового почтового ящика идентификатор и полное состояние **уже созданного** запланированного письма, отличая ID сообщения от ID задания по расписанию.
2. По официальному клиенту Mail.ru определить существующую операцию «Отправить сейчас» над этим объектом, точные параметры запроса и ответы, без предположений о маршруте.
3. На тестовом письме с будущим временем и единственным собственным адресатом проверить, что операция изменяет именно исходное задание, и что после неё исходное расписание отсутствует.
4. Сверить отправленные сообщения и фактическую доставку в течение исходного интервала расписания — один исходный ID и не более одной отправки.
5. Проверить отказ, тайм-аут, повторное нажатие, два одновременных запроса и восстановление после перезапуска; не допустить повторной отправки после неопределённого ответа.
6. Только после этого включить одиночное и массовое действие и добавить воспроизводимые автономные испытания.

Исследовательские внешние запросы выполняются с интервалом **не менее 5 секунд**. Секреты, токены и полные тексты писем в репозиторий не загружать.

**Решение:** не включать потенциально опасную команду без протокольного и сквозного подтверждения. Это открытый технический долг, не функция v0.3.30.

## 14.10.2026 — согласованная реализация: создать копию, удалить расписание, отправить

Владелец отверг необходимость поисковой функции в официальном приложении
и прямо согласовал пользовательский алгоритм:
**полностью подготовить независимую копию → удалить прежнее запланированное
письмо → отправить новую копию немедленно**. Ранее созданный исследовательский
PR #169 закрыт без слияния; никаких аналитических инструментов в MailRu Desktop
не добавляется.

В PR #170 реализованы общие действия для кнопки в письме, контекстного
меню и выделенных исходящих; используется один `ScheduledSendNowExecution`.
Операция не является атомарной транзакцией сервера, поэтому:
- загрузка и повторное добавление вложений выполняются до удаления;
- при ошибке подготовки исходное письмо не затрагивается;
- удаление выполняется штатным `/api/v1/messages/remove`;
- перед отправкой запрашивается актуальное состояние исходящей папки и
  проверяется отсутствие прежнего ID; при неоднозначности отправки **нет**;
- только после проверки отправляется копия с `send_date=0`;
- при ошибке или тайм-ауте подтверждения отправка никогда не повторяется
  автоматически. Следует вручную проверить «Отправленные»;
- при массовой операции каждая запись обрабатывается последовательно,
  первая неопределённость останавливает оставшуюся очередь;
- перед началом пользователь подтверждает действие в отдельном диалоге;
- HTML с `cid:` не клонируется до доказанного переноса связанных
  встроенных изображений.

Ограничение доказательств: **исчезновение старого ID из папки не доказывает
само по себе прекращение серверного фонового задания**. Поэтому действие
требует явного подтверждения с предупреждением о возможности повторной
доставки. По решению владельца отдельные испытательные сборки запрещены,
функция выпускается только через штатный GitHub Release с версией 0.3.72.
Первое живое испытание проводить на одном письме себе, отложенном на
ближайшее контролируемое время: проверить немедленную доставку и отсутствие
второй доставки после прежнего срока. До этого не использовать массовую
операцию для значимых рассылок. Автоматические тесты не заменяют проверку
отмены расписания на реальном сервере.

Токены, содержимое писем и сырые серверные ответы в публичные тесты не
попадают. Проверки делаются синтетическими ответами и автономными функциями.

## 14.10.2026 — решение владельца после испытания v0.3.72

Владелец проверил функцию и получил остановку на этапе удаления
исходного расписания. Согласован новый порядок для v0.3.73:

1. Полностью получить исходное письмо, сохранить всех доступных получателей,
   тему, текст/HTML, приоритет. Вложения скопировать в новую отправку.
   При неполной копии ничего не отправлять и не перемещать.
2. **Сразу отправить клонированное письмо** стандартным серверным методом.
3. **Только при подтверждённой отправке** перенести исходное отложенное
   письмо из папки «Исходящие» в папку «Корзина» (ID 500002)
   штатной операцией `/api/v1/messages/move`. Не удалять оригинал
   окончательно.
4. Если отправка не подтверждена — оригинал не перемещать. Если отправка
   подтверждена, но перенос не удался — не отправлять копию повторно.
5. Во время работы **не показывать модальные диалоги** подтверждения,
   предупреждения или ошибок; писать компактный результат в имеющуюся
   строку состояния и техническую диагностику.
6. Для кнопки письма, контекстного меню и групповой операции использовать
   один исполнитель; групповой режим последовательный и прекращается
   при первой ошибке или неопределённом ответе.

Синтетические испытания охватывают порядок отправки/перемещения, ошибку
подготовки, потерю ответа отправки, отказ и потерю ответа перемещения,
смену аккаунта. Живая проверка отмены исходного фонового расписания после
перемещения в Корзину **не проведена**. Это принципиальное ограничение:
при неотменённом задании письмо может прийти второй раз в назначенное
время. Первый опыт — только на собственном тестовом адресе, включая
проверку после первоначального срока.

Историческое описание первоначального варианта «сначала удаление,
затем отправка» выше оставлено как описание v0.3.72; текущим
согласованным поведением для v0.3.73 является именно **отправка →
Корзина**. Экспериментальные сборки не использовать.
